# Hostinger Deployment

## Purpose

This document describes how the Moving in Mobile website is deployed to Hostinger, how staging and production environments are separated, and what hosting-specific configuration is required for the React/Vite application to operate correctly.

The deployment workflow is intentionally conservative. Changes should be validated on staging before they are promoted to production.

## Hosting Platform

The Moving in Mobile website is hosted on Hostinger.

The application is deployed as a Vite front-end web application connected to the GitHub repository.

The current application stack does not use a custom Express server or a persistent Node application process for normal request handling.

The production build is generated by Vite and served by Hostinger.

## Environments

Two public environments are maintained.

### Production

Production URL:

`https://movinginmobile.com`

Production source branch:

`main`

Only validated application changes should be promoted to production.

### Staging

Staging URL:

`https://staging.movinginmobile.com`

Development source branch:

`staging`

Hostinger staging deployment branch:

`redesign-v2`

The `redesign-v2` branch exists specifically because Hostinger watches that branch for the staging deployment.

It is fed from `staging`.

## Standard Git and Deployment Workflow

Development begins on:

`staging`

The standard workflow is:

```text
Local development
      |
      v
staging
      |
      v
origin/staging
      |
      v
origin/redesign-v2
      |
      v
Hostinger staging
      |
      v
Validation
      |
      v
Merge staging into main
      |
      v
origin/main
      |
      v
Hostinger production
```

The normal commands are:

```bash
git checkout staging
git pull origin staging
```

After development and local validation:

```bash
git add <files>
git commit -m "Describe the change"
git push origin staging
```

To deploy the current staging commit to Hostinger staging:

```bash
git push origin staging:redesign-v2
```

After staging validation:

```bash
git checkout main
git pull origin main
git merge staging
git push origin main
```

After production deployment and validation:

```bash
git checkout staging
```

This returns the local working branch to the normal development branch.

## Build Process

The application is built using:

```bash
npm run build
```

The command invokes Vite.

The generated production output is written to:

`dist/`

A successful build should complete before code is pushed to staging.

Do not edit files in `dist/` as the normal method of making application changes.

`dist/` is generated output.

Application changes should be made in source-controlled files and regenerated through the Vite build.

## Vite Configuration

The current Vite configuration is maintained in:

`vite.config.js`

The site uses:

```javascript
base: "/"
```

This is appropriate because the production website is served from the root of:

`movinginmobile.com`

and the staging website is served from the root of:

`staging.movinginmobile.com`

The historical GitHub Pages deployment used a subdirectory path, but the current Hostinger deployment uses root-domain hosting.

Future developers should not change the Vite base path back to the historical GitHub Pages configuration unless the deployment architecture changes.

## React Router Hosting Requirement

The application uses React Router with `BrowserRouter`.

Browser routes include:

* `/`
* `/about`
* `/buyers`
* `/sellers`
* `/neighborhoods`
* `/rowe-report`
* `/resources`
* `/contact`

React Router handles these routes in the browser.

However, when a user directly requests a URL such as:

```text
https://movinginmobile.com/buyers
```

Hostinger receives the request before React executes.

Without fallback routing, Hostinger attempts to find a physical file or directory named:

`/buyers`

If none exists, Hostinger returns HTTP 404.

This behavior was discovered during the React Router staging rollout on August 12, 2026.

## SPA Fallback Configuration

The React Router direct-route problem is solved using:

`public/.htaccess`

The current source-controlled configuration is:

```apache
RewriteEngine On

# Preserve Hostinger's internal builds protection
RewriteRule ^\.builds - [F,L]

# Serve existing files and directories normally
RewriteCond %{REQUEST_FILENAME} -f [OR]
RewriteCond %{REQUEST_FILENAME} -d
RewriteRule ^ - [L]

# React Router SPA fallback
RewriteRule ^ index.html [L]
```

Vite copies `public/.htaccess` into the build output.

This causes Hostinger to:

1. block access to Hostinger's internal `.builds` path;
2. serve physical files normally;
3. serve physical directories normally;
4. return `index.html` for application routes that do not correspond to physical files.

React Router then reads the browser pathname and renders the appropriate page.

## Why the Rewrite Rule Is Source-Controlled

The SPA fallback was initially tested by editing `.htaccess` directly through Hostinger File Manager.

The test successfully resolved direct-route 404 errors.

The configuration was then added to:

`public/.htaccess`

so the hosting behavior is reproduced automatically by future deployments.

Deployment-critical configuration should be source-controlled where practical.

A future deployment must not rely solely on an undocumented manual Hostinger change.

## Static Files and Rewrite Behavior

The fallback rule intentionally preserves existing files and directories.

Therefore these resources should continue to load directly:

```text
/robots.txt
/sitemap.xml
/assets/...
/images and other public assets
```

Only non-file application routes are rewritten to:

`index.html`

This behavior must be verified after changes to `.htaccess` or routing.

## Routing Validation

After any deployment that changes React Router or `.htaccess`, test direct requests.

At minimum:

```text
https://staging.movinginmobile.com/buyers
https://staging.movinginmobile.com/sellers
https://staging.movinginmobile.com/rowe-report
```

For each route:

1. open the URL directly in a new browser tab;
2. confirm the correct React page loads;
3. refresh the browser;
4. confirm the page still loads and does not return 404.

Also validate:

```text
https://staging.movinginmobile.com/robots.txt
https://staging.movinginmobile.com/sitemap.xml
```

Equivalent tests must be performed in production after promotion.

## Staging Validation

Before merging staging into production, validate the relevant parts of the application.

Typical checks include:

* homepage rendering;
* desktop navigation;
* mobile navigation;
* route URLs;
* direct-route refresh;
* browser Back and Forward;
* responsive behavior;
* lead forms;
* modal behavior;
* analytics;
* canonical URLs;
* structured data where affected;
* `robots.txt`;
* sitemap;
* branding and compliance elements.

Major integrations should receive additional integration-specific testing.

## Production Promotion

After staging validation succeeds:

```bash
git checkout main
git pull origin main
git merge staging
git push origin main
```

Allow Hostinger to complete the deployment.

Then validate production.

Do not assume that a successful Git push guarantees a successful production deployment.

Check both:

* Hostinger deployment status;
* live site behavior.

## Production Validation

At minimum, after a material production deployment validate:

```text
https://movinginmobile.com/
https://movinginmobile.com/buyers
https://movinginmobile.com/sellers
```

For routing-related releases also validate:

```text
https://movinginmobile.com/about
https://movinginmobile.com/neighborhoods
https://movinginmobile.com/rowe-report
https://movinginmobile.com/resources
https://movinginmobile.com/contact
```

Directly load at least one nested route and refresh it.

Also verify:

```text
https://movinginmobile.com/robots.txt
https://movinginmobile.com/sitemap.xml
```

## Hostinger File Manager

Hostinger File Manager may be useful for:

* inspecting deployed files;
* confirming server-side files exist;
* temporarily validating a hosting hypothesis;
* reviewing `.htaccess`;
* troubleshooting deployment behavior.

It should not normally be used as the permanent source of application changes.

If a manual Hostinger change becomes necessary for normal runtime behavior, document it and determine whether it can be reproduced from the repository.

The `.htaccess` SPA fallback is an example of a manual discovery that was subsequently moved into source control.

## Hostinger Internal Build Protection

The Hostinger environment contained this existing rewrite rule:

```apache
RewriteRule ^\.builds - [F,L]
```

This rule protects Hostinger's internal build directory.

It was preserved when the SPA routing rules were introduced.

Do not remove Hostinger-specific protection rules without understanding their purpose.

## Branch Safety

The branch roles are operationally important.

Do not casually change:

* production branch mapping;
* staging branch mapping;
* Hostinger watched branch;
* staging deployment process.

If branch mappings change, update:

* this document;
* `06-git-branching-workflow.md`;
* `20-decision-log.md`;
* deployment checklists;
* onboarding documentation.

## Documentation-Only Changes

Documentation changes under:

`docs/`

do not need to be deployed to Hostinger solely to be stored in GitHub.

For documentation-only work:

```bash
git push origin staging
```

is sufficient to store the changes in the repository.

A push to:

```bash
git push origin staging:redesign-v2
```

is only required when the staging website itself needs to receive the change.

Documentation describing the production architecture should eventually be promoted to `main`.

## External Hosting Configuration

Not all Hostinger configuration is represented in Git.

Examples may include:

* domain assignment;
* SSL;
* deployment connection;
* branch selection;
* environment settings;
* DNS;
* provider-managed infrastructure.

The repository documents expected behavior, but the live Hostinger configuration remains authoritative for provider-side settings.

## Deployment Troubleshooting

### Build fails locally

Run:

```bash
npm run build
```

Review the first compiler or Vite error.

Correct source code rather than editing generated files.

### Staging does not contain the newest commit

Check:

```bash
git status
git log -1 --oneline
```

Confirm `staging` contains the intended commit.

Then push:

```bash
git push origin staging
git push origin staging:redesign-v2
```

Confirm Hostinger completes the deployment.

### Direct React route returns 404

Check:

`public/.htaccess`

Confirm the deployed `.htaccess` contains the SPA fallback rules.

Also verify that real files such as:

`robots.txt`

and:

`sitemap.xml`

still load.

### Homepage works but nested route fails after refresh

This strongly indicates an SPA fallback problem rather than a React Router component problem.

Validate `.htaccess` before modifying application route logic.

### Staging works but production fails

Compare:

* deployed commit;
* branch;
* Hostinger deployment status;
* `.htaccess`;
* domain-specific configuration;
* browser console;
* network requests.

Do not assume staging and production provider configuration are identical.

## Rollback Principles

If a production release causes a material regression:

1. capture the failing commit and symptoms;
2. determine whether the issue is application code, build output, hosting configuration, or an external provider;
3. restore the last known-good production state if impact is significant;
4. reproduce and fix the issue on staging;
5. validate before redeployment;
6. document the root cause and prevention steps.

Lead capture, core navigation, compliance identity, and site rendering should receive rollback-first consideration when materially broken.

## Deployment-Related Security

Do not commit:

* account passwords;
* private API keys;
* tokens;
* provider secrets.

Do not expose private credentials through browser-delivered Vite environment variables.

Remember that standard client-side Vite code is visible to site visitors after build.
